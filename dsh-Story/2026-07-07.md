## 2. 设计模式与重构

- **应用的设计模式**：
  - **Strategy Pattern** — `session modes` 引入了 per-agent 策略状态机（plan mode / default mode），agent 的行为通过 mode 策略切换，而非硬编码在循环逻辑中
  - **Event Sourcing** — recallable compaction RFC 提出 split checkpoints + in-session history recall，本质是将 session log 的 checkpoint 机制与历史回放能力解耦
  - **Seam Pattern (Capability Seam)** — agent/request-messages seam 延续了 Service Definition / Provider / Consumer 三角色模式，在 agent loop 的请求阶段插入 request-only message 通道

- **模块解耦与接口定义**：
  - `system-prompt` 的 `TOOL_ORDER_REST` 从 `'...'` 重命名为 `'<unlisted-tools>'`（`72933ec558`），明确语义：这是未注册工具的占位符而非省略号
  - agent/request-messages seam（`17bd71e530`）定义了 agent loop 中 request 阶段的 message 注入点，为后续的 session-prefix 和 request-advice 演进奠定基础
  - export-JSDoc gate 在多个包间同步推进（`1f5db6e0b0`, `aeaccf6d36`），强制所有 public export 携带 JSDoc，属于编译期契约治理

- **基础设施与性能**：
  - Node 引擎范围从 `>=22.19` 降低到 `^22.18.0 || >=24.0.0`（`9296411ea1`, `f33e14ff19`），排除 EOL 的 Node 23，扩大兼容性窗口
  - `globSync` 替代 async fs glob（`1c2823c73d`）修复 Node 22.18 上的兼容性问题

## 3. 特性交付与系统影响

- **核心特性**：
  - **Session Modes**（`2602270669`）— plan mode 作为 logged per-agent policy state，mode 状态持久化在 session log 中，每次 agent 行为切换都可追溯
  - **Recallable Compaction**（`0056238bbd`）— 将 compaction 的 checkpoint 与 in-session history recall 分离，允许 agent 回溯到 compaction 前的上下文
  - **MCP Client Plugin**（`1fbe7c39d4`）— `dsh-mcp-client` 插件引入，使 harness 能作为 MCP client 连接外部 MCP server
  - **Agent/Request-Messages Seam**（`17bd71e530`）— 在 agent loop 的 request 阶段提供 message 注入能力，为 session-prefix 演进铺路

- **系统拓扑影响**：
  - session modes 改变了 agent 的行为决策路径，mode 状态成为 session log 的一等公民
  - MCP client 扩展了 harness 的外部集成边界，与 typert 的 type registry 和 tools 的 tool registry 形成新的对接点
  - structured-output subagent seam 的修复（`0e0f3b2f19`, `280233ba78`）影响 subagent 的 capture 语义，structured runtime 改为 per-run 获取而非 per-backend

## 4. 架构决策与 Roadmap 对齐

- **关键技术决策（ADR 推断）**：
  - **背景与痛点**：agent 在长对话中需要"计划模式"来暂停执行、审查方案、分步推进，但当前 session log 没有记录 agent 的策略状态，导致 mode 切换不可追溯
  - **选择的方案**：将 mode 状态作为 session event 记录，plan mode 作为 per-agent policy state，通过 RFC 驱动设计
  - **Trade-offs**：增加了 session log 的事件类型，但获得了完整的 mode 变更审计链路；选择 RFC 而非直接实现，表明团队在权衡设计完备性与交付速度

  - **背景与痛点**：compaction 会丢失历史上下文，agent 无法回溯到 compaction 前的决策
  - **选择的方案**：split checkpoints + in-session history recall，将 compaction 的"总结"与"可回溯性"分离
  - **Trade-offs**：增加了 checkpoint 管理的复杂度，但保留了 agent 的历史决策能力

- **产品 Roadmap 支撑**：
  - Session modes 是 plan mode 产品化的技术基础，直接支撑 "agent 可以分步审查和执行" 的产品能力
  - MCP client 支撑 "连接外部工具生态" 的产品愿景
  - structured-output subagent seam 的修复确保 subagent 的结构化输出在 session log 中正确记录

## 5. 开发者/架构师决策推断

  - **优先级选择**：先做 RFC 设计（session modes、recallable compaction），再做基础设施（MCP client、request-messages），最后做修复和治理（tool order、catalog、JSDoc gate）

- **架构师决策推断**：
  - **模块拆分粒度**：session modes 作为独立包 `dsh-mode` 而非嵌入 core，遵循了 capability seam 的三角色模式（Service Definition in core, Provider in dsh-mode, Consumer in agent-loop）
  - **抽象层引入时机**：agent/request-messages 在 structured-output subagent seam 修复后引入，说明团队认识到 agent loop 的 request 阶段需要一个稳定的 message 注入点，而非在每个 consumer 中硬编码
  - **后续影响**：session modes 的 RFC 设计为后续的 plan mode 实现、sandbox/approval switching、exit_plan_mode 等一系列特性奠定了架构基础

- **Code Review 视角**：
  - **首先关注**：`0e0f3b2f19`（structured runtime per run 而非 per backend）— 这是一个关键的语义变更，会影响所有 structured-output 的 capture 行为
  - **会提出的问题**：session modes 的 mode 状态与 agent 的 quiescence 边界如何交互？mode 切换是否需要等待当前 step 完成？
  - **做得好**：tool order 的语义修正（`72933ec558`）非常精准，将 `'...'` 重命名为 `'<unlisted-tools>'` 消除了歧义
  - **可以改进**：多个 RFC 在同一天提交（session modes、recallable compaction），可能存在交叉依赖未充分讨论
