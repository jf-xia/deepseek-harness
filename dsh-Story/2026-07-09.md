## 2. 设计模式与重构

- **应用的设计模式**：
  - **Scoped Context Pattern** — dsh-scope 引入了 scoped-context registration primitive，agent 成为 registration scope（`f387b774a9`），每个 agent 有独立的 `Agent.ctx`，setup slot 控制 scope 的生命周期
  - **Facade Pattern** — tool-cordis 的 whitelist façade（`1b1ba96d4f`）替代了 pass-through ctx proxy，通过白名单控制 agent 对 runtime 的访问
  - **Registry Pattern** — scope-aware registries（`3d16026eb0`）使 registry 支持 scoped registration，fused scoped dispatch 实现了跨 scope 的事件分发
  - **Template Method** — background task runtime 定义了 task 的生命周期模板，bash/subagent producers 实现具体的 task 执行

- **模块解耦与接口定义**：
  - `dsh-scope` 作为独立 primitive（`32db205c10`）而非嵌入 core，提供了通用的 scoped-context registration 能力
  - tool-cordis 从 inspect plugins section 扁平化为 capability list（`ea66641b84`），简化了 plugin 的发现和注册
  - transcript renderer 提取为 `dsh-compact`（`fc6db791f1`），使 compaction 和 session 的 transcript 渲染共享实现

- **基础设施与性能**：
  - workflow engine 从 VM 切换到 worker-thread（`b5f618bcfb`），提供了更好的隔离和性能
  - registry register-method 统一返回 effect disposer（`7c5133488a`），确保所有注册都可以被正确清理

## 3. 特性交付与系统影响

- **核心特性**：
  - **Agent Scoping**（`f387b774a9`）— agent 成为 registration scope，`Agent.ctx` 提供独立的 context，setup slot 控制 scope 生命周期
  - **Tool Cordis**（`ee1da1ce5b`）— `@deepseek-ai/dsh-tool-cordis` 提供 inspect/mount/unmount over live runtime，使 agent 能自省和修改自己的 runtime
  - **Background Task Runtime**（`184e164091`）— background task runtime + generic task_* control tools + bash/subagent producers
  - **Glob/Grep Discovery Tools**（`e0f20088d8`）— bash-backed glob/grep 工具，使 agent 能搜索文件系统

- **系统拓扑影响**：
  - agent scoping 改变了 agent 的注册和分发模型，从 global registry 变为 scoped registry
  - tool-cordis 扩展了 agent 的自省能力，agent 可以 inspect 和 modify 自己的 runtime
  - background tasks 为 agent 提供了异步执行能力，task_* tools 成为 agent 的控制接口

## 4. 架构决策与 Roadmap 对齐

- **关键技术决策（ADR 推断）**：
  - **背景与痛点**：当前 agent 共享 global registry，无法隔离不同 agent 的注册和事件分发
  - **选择的方案**：引入 dsh-scope primitive，agent 成为 registration scope，每个 agent 有独立的 `Agent.ctx`
  - **Trade-offs**：增加了 scope 管理的复杂度，但获得了 agent 间的隔离性；选择 scoped-context 而非 actor model，是因为 Cordis 的 plugin 体系已经提供了 context 机制

  - **背景与痛点**：agent 需要自省和修改自己的 runtime，但当前的 ctx proxy 暴露了过多的内部细节
  - **选择的方案**：引入 tool-cordis 的 whitelist façade，通过白名单控制访问
  - **Trade-offs**：增加了维护白名单的成本，但获得了更好的封装性

  - **背景与痛点**：agent 需要异步执行长时间运行的任务，但当前的 tool 执行是同步的
  - **选择的方案**：引入 background task runtime + task_* control tools
  - **Trade-offs**：增加了 task 管理的复杂度，但获得了异步执行能力

- **产品 Roadmap 支撑**：
  - agent scoping 支撑 "多 agent 协作" 的产品能力，每个 agent 有独立的注册空间
  - tool-cordis 支撑 "agent 自省和修改" 的产品能力，为 self-modification 插件奠定基础
  - background tasks 支撑 "异步任务执行" 的产品能力，为长时间运行的任务提供支持

## 5. 开发者/架构师决策推断

- **开发者意图重建**：
  - **思维模型**：开发者在同一天推进了 agent scoping、tool-cordis、background tasks、workflow engine 切换四个方向，说明他在构建"agent 的自治与隔离"基础设施——agent 需要独立的注册空间（scoping），需要自省能力（tool-cordis），需要异步执行（background tasks），需要更好的隔离（worker-thread）
  - **优先级选择**：先做 dsh-scope primitive（`32db205c10`），再做 agent scoping（`f387b774a9`），再做 tool-cordis（`ee1da1ce5b`），最后做 background tasks（`184e164091`），遵循"基础→集成→扩展"的顺序
  - **有意取舍**：agent scoping 选择 scoped-context 而非 actor model，是因为 Cordis 的 plugin 体系已经提供了 context 机制，引入 actor model 会增加不必要的复杂度

- **架构师决策推断**：
  - **模块拆分粒度**：dsh-scope 作为独立 primitive 而非嵌入 core，提供了通用的 scoped-context registration 能力，可以被其他模块复用
  - **抽象层引入时机**：在 Code Mode 和 tool governance 稳定后引入 agent scoping，是因为 scoping 需要与现有的 tool registry 和 session log 协调
  - **后续影响**：agent scoping 为后续的多 agent 协作、agent 间通信、agent 隔离等特性奠定了架构基础

- **Code Review 视角**：
  - **首先关注**：`f387b774a9`（agent is a registration scope）— 这是一个核心架构变更，会影响所有 agent 的注册和分发行为
  - **会提出的问题**：scoped dispatch 的性能影响是什么？跨 scope 的事件分发是否有 overhead？scope 的生命周期如何与 agent 的生命周期对齐？
  - **做得好**：tool-cordis 的 whitelist façade（`1b1ba96d4f`）设计非常精巧，通过白名单控制访问，既保证了封装性又提供了灵活性
  - **可以改进**：background task runtime 的 task_* tools 命名不够一致（task_start、task_wait、task_cancel），建议统一为 task. 前缀
