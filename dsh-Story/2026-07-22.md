## 2. 设计模式与重构

### 应用的设计模式

- **Canonical Output Pattern**：将工具输出标准化为统一格式（`canonicalize terminal outputs`），通过共享 `terminal task schema` 实现跨组件一致性。这是典型的 **Adapter Pattern** 应用，将不同终端工具的输出统一为规范格式。
- **Packed Chunk Storage**：JSONL 存储采用打包行格式（packed chunk rows），体现了 **Repository Pattern** 的变体，通过序列化策略优化存储效率。
- **Goal Wire Domain**：引入 Goal Wire Domain 和 Goal Bar 组件，采用 **Domain Events** 模式将目标状态与 UI 渲染解耦。

### 模块解耦与接口定义

- **PTY 生命周期清理**：`pty: preserve startup cancellation and zombie cleanup` 和 `pty: close retained lifecycle review gaps` 表明对 PTY 模块进行了严格的生命周期边界定义，将启动取消与僵尸进程清理职责分离。
- **Schema DSL 与 Canonical Tool Output 分层**：通过 `tool-json-schema-dsl` → `canonical-tool-output` → `code-mode-typed-results` 的依赖链，建立了清晰的类型传递管道。
- **Plan Mode 简化**：`refactor(plan): remove generic mode abstraction` 移除了过度抽象的 mode 通用层，回归具体实现。

### 基础设施与性能

- **CI 合并 Runner**：`ci: consolidate gates on large runners` 和 `ci: use four-core hosted runners` 通过合并 gate 任务减少 CI 冷启动开销。
- **Coverage 并发控制**：`ci: bound coverage worker forks` 和 `ci: process-safe coverage pools` 解决了覆盖率测试的并发竞争问题。
- **快照测试优化**：`test(snapshot): cover all packed chunk row kinds` 确保所有打包行类型都有测试覆盖。

## 3. 特性交付与系统影响

### 核心特性

- **Goal 系统 UI**：`feat(gui): goal wire domain, client goal state, and docked goal bar` 引入了目标跟踪的完整 UI 层，从 domain 到 wire 到 rendering 的全栈实现。
- **PTY 持久会话**：PR #467 `feature/persistent-pty-sessions` 完成了持久化终端会话的生命周期管理。
- **Session Reference 绑定**：`fix(session-reference): bind snapshots to prompts` 将快照与提示绑定，确保会话引用的一致性。
- **Web Session Title 投影**：`feat(web): render durable session titles` 和 `feat(web): generate model-backed session titles` 实现了基于模型的会话标题生成。

### 系统拓扑影响

- **PTY 模块重构**影响了 shell、terminal、subprocess 等下游包的交互方式。
- **Tool Output 标准化**改变了所有工具消费者处理输出的契约。
- **CI 合并**影响了所有 PR 的验证流程和开发者体验。

## 4. 架构决策与 Roadmap 对齐

### 关键技术决策（ADR 推断）

- **背景与痛点**：PTY 模块存在生命周期管理不完整的问题（zombie processes、startup cancellation 不保留），同时 CI 系统因分散的 gate 任务导致冷启动开销大。
- **选择的方案与 Trade-offs**：
  - PTY：选择在 `packages/terminal` 中统一处理生命周期，而非分散在各 provider 中。牺牲了部分灵活性，换取了一致的清理保证。
  - CI：选择合并到大型 runner，牺牲了并行度，换取了更少的冷启动次数。
  - Tool Output：选择通过 DSL 生成 schema，而非手写，增加了构建复杂度，但保证了类型一致性。

### 产品 Roadmap 支撑

- Goal 系统 UI 支撑了用户可见的任务跟踪功能。
- 持久化 PTY 会话支撑了开发者工具链的连续性。
- Session Title 投影支撑了 Web 端的会话管理体验。

## 5. 开发者/架构师决策推断

### 开发者意图重建

- **思维模型**：开发者在 7 月 22 日面临多个并行工作流的合并压力（PTY review fixes、canonical tool output stack、session reference、plan mode），需要在保持主干稳定的同时推进多个特性分支。
- **优先级选择**：优先处理 PTY 生命周期问题（影响用户体验），然后是 tool output 标准化（影响多个下游组件），最后是 UI 细节（goal bar、sidebar）。
- **有意取舍**：Plan Mode 的 generic mode abstraction 被有意移除，说明团队判断过度抽象的维护成本高于收益。

### 架构师决策推断

- **模块拆分粒度**：PTY 模块的拆分粒度从 provider 级别提升到 session 级别，反映了对"会话作为一等公民"的架构判断。
- **抽象层引入时机**：Schema DSL 的引入时机恰到好处——在 tool output 标准化需求明确后，而非过早抽象。
- **对后续可扩展性的影响**：Goal Wire Domain 的引入为后续的任务编排、工作流引擎奠定了基础。

### Code Review 视角

- **首先关注**：PTY 生命周期清理（zombie cleanup）——这类问题如果处理不当会导致资源泄漏。
- **会提出的问题**：
  1. PTY startup cancellation 的保留是否会影响现有 provider 的行为？
  2. Canonical tool output 的 schema 变更是否向后兼容？
  3. Goal Bar 的 wire domain 是否考虑了离线场景？
- **做得好**：Tool output 的分层设计（DSL → Canonical → Typed）非常清晰。
- **可以改进**：CI 合并的决策缺少 ADR 记录，后续维护者可能不理解为什么选择大型 runner。

## 6. 技术债务与风险评估

### 已知风险 / 变通方案

- **PTY zombie cleanup**：虽然添加了清理逻辑，但 `close retained lifecycle review gaps` 暗示仍有边界情况需要覆盖。
- **Packed Chunk Rows**：新的存储格式与旧格式的兼容性需要关注，`test(snapshot): cover all packed chunk row kinds` 是好的开始。
- **Goal UI 的 CI 覆盖**：`ci: coverage defer goal-ui wire tails (TODO(gui))` 明确标记了覆盖率缺口。

### 建议的下一步

1. 为 PTY 生命周期清理添加集成测试，覆盖所有 provider 组合。
2. 为 canonical tool output 的 schema 变更添加向后兼容性测试。
3. 补充 Goal Wire Domain 的单元测试和集成测试。
