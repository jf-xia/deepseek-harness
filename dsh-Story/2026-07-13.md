## 2. 设计模式与重构

- **应用的设计模式**:
  - **Adapter Pattern**: MCP tool naming（`af3152fefe`）采用 server-qualified 命名，将 MCP 的 tool namespace 从隐式映射转为显式 qualified 形式
  - **Factory Pattern**: Single-exe 的 closure manifest（`bd831db80b`）将构建产物的声明与构建逻辑分离
  - **Repository Pattern**: Python SDK 的 runtime carrier packages（`ade150b719`）将 Python runtime 作为独立的可分发单元

- **模块解耦与接口定义**:
  - `narrow synchronous extension contracts`（`f32cfafa1a`）将同步扩展的 contract 收窄，减少了不必要的 surface
  - `remove owner-final assembly machinery`（`e04ec07345`，跨天 merge）消除了 assembly-time 的不确定性
  - `simplify session log representation`（`1123e946c0`）精简了 session log 的内部表示，减少了序列化/反序列化的复杂度

- **基础设施与性能**:
  - `perf(session-query): keep provenance validation linear`（`be0d44183d`）将 provenance validation 从可能的指数复杂度优化为线性
  - `optimize workspace instruction change detection`（`a0e917ffe3`）减少了 workspace context 的检测开销

## 4. 架构决策与 Roadmap 对齐

- **关键技术决策（ADR 推断）**:
  - **背景与痛点**: Python runtime 的分发依赖于 Node.js 的构建管道，缺乏独立的 packaging 和 CI workflow。Single-exe 的需求来自 SDK 用户希望零依赖部署
  - **选择的方案与 Trade-offs**: Python SDK 采用 "carrier package" 模式（`deepseek-harness` + `deepseek-harness-runtime`），牺牲了单一包的简洁性换取了分发的灵活性。Single-exe 采用 closure manifest 模式，将所有依赖打包进一个文件，牺牲了更新的粒度换取了部署的简便性
  - **隐式决策**: MCP 采用 server-qualified naming 表明团队决定遵循 MCP 社区的标准约定，而非自定义命名空间

- **产品 Roadmap 支撑**:
  - Python SDK 支撑了 Python 生态的 agent 开发
  - Single-Exe 支撑了 SDK 的"零配置"部署场景
  - MCP 标准化支撑了与第三方 MCP server 的集成
  - Session-Query 关系追踪支撑了调试和审计需求

## 5. 开发者/架构师决策推断

- **开发者意图重建**:
  - 开发者的思维模型是：**SDK 必须有多语言、多分发渠道的支持**。Python SDK 和 Single-Exe 是同一枚硬币的两面——Python 面向 Python 开发者，Single-exe 面向需要零依赖部署的场景
  - 优先级排序：(1) Python SDK 分发 (2) Single-exe 构建 (3) MCP 标准化 (4) Session-Query 追踪 (5) 权限预设
  - 有意取舍：Python SDK 的 "carrier package" 模式是一个有意的 complexity trade-off——更复杂的 packaging 换取更灵活的分发

- **架构师决策推断**:
  - 模块拆分粒度：Python SDK 被拆分为 `deepseek-harness`（SDK）和 `deepseek-harness-runtime`（runtime），说明团队认为 SDK 和 runtime 的演进速度不同
  - 抽象层引入时机：MCP tool naming 的标准化在 Single-exe 之前完成，是因为 MCP 是 Single-exe 的上游依赖
  - 后续影响：Python SDK 的引入意味着所有后续的 capability 都需要考虑 Python binding 的可行性
  - 作为架构师，我会质疑 Single-exe 的 closure manifest 是否会导致 binary 膨胀，以及 Python SDK 的 wheel 构建是否支持 cross-platform

- **Code Review 视角**:
  - 首先关注：Python SDK 的 `derive release version from repository`（`fe3777cf27`）——需要确认版本派生逻辑是否与 npm 生态一致
  - 提出的问题：(1) Single-exe 的 worker-backed tools 如何在 closed environment 中工作？(2) MCP server-qualified naming 是否向后兼容？
  - 做得好：Python SDK 的分发管道从 packaging 到 CI 发布形成了完整的闭环
  - 可改进：Single-exe 的 CI workflow 可以考虑添加 binary 大小监控

## 6. 技术债务与风险评估

- **已知风险 / 变通方案**:

  - 为 Python SDK 添加 integration test，验证 runtime lifecycle 的正确性
  - 为 Single-exe 添加 binary 大小 regression test
  - 为 MCP server-qualified naming 添加 backward compatibility test

### 阶段 1: Python SDK 分发体系构建

**涉及的 Commits**: `ade150b719`, `283ac7f097`, `cdd11ac587`, `ef2754110a`, `fe3777cf27`, `5d913a796a`

**阶段意图**: 构建完整的 Python SDK 和 runtime 分发体系，包括 packaging、wheel 构建、CI 发布、版本派生。

**开发者视角推断**:
- **思维模型**: 开发者的脑中是一个完整的 Python 分发管道——从 package 定义到 wheel 构建到 CI 发布到版本派生，每个环节都必须可靠
- **优先级选择**: 先定义 package 结构（carrier + runtime），再实现构建管道，最后添加 CI 发布
- **有意取舍**: 选择 "carrier package" 模式而非单一包，是因为 runtime 的 platform-specific 依赖需要独立的 wheel

**架构师视角推断**:
- **粒度考量**: 将 SDK 和 runtime 拆分为两个 package，说明团队认为它们的演进速度不同——SDK 频繁变更，runtime 相对稳定
- **时机判断**: 在 Node.js SDK 稳定后立即构建 Python SDK，是因为 Node.js 的实现为 Python binding 提供了 reference implementation
- **后续影响**: Python SDK 的引入意味着所有后续的 capability 都需要考虑 Python binding，增加了跨语言一致性的约束

**重点关注的文档/代码**:

| Python SDK | `python/` | package 结构和 API surface |
| Runtime wheels | `python/runtime/` | platform-specific wheel 的构建 |
| CI pipeline | `.github/workflows/` | Python SDK 的发布流程 |

**关键代码模式**:
```python
# deepseek-harness: SDK package
# deepseek-harness-runtime: runtime carrier
# 平台特定的 wheel 构建通过 CI matrix 实现
```

**领域建模洞察**（DDD 视角）:
- Python SDK 作为 **Bounded Context**，与 Node.js SDK 共享核心 domain 但有不同的 language binding
- Runtime carrier 作为 **Value Object**，描述了 runtime 的平台依赖
- Version derivation 作为 **Domain Service**，确保 Python 和 Node.js 的版本一致性

- **后续影响**: Single-exe 将成为 SDK 的主要分发方式之一，影响后续的版本管理和更新策略

### 阶段 3: MCP 标准化与 JSONRPC 改造

**涉及的 Commits**: `af3152fefe`, `67fe6c10b6`, `7696f88d9f`, `e547980d77`

**阶段意图**: 采用主流的 MCP tool naming 标准，同时将 JSONRPC SDK serving surface 改造为 plugin 架构。

**开发者视角推断**:
- **思维模型**: 开发者在执行"标准化 + 重构"——MCP 命名遵循社区标准，JSONRPC 从 monolith 拆分为 plugins
- **优先级选择**: 先标准化 MCP naming（消除与社区的 friction），再重构 JSONRPC serving surface（提升可扩展性）
- **有意取舍**: server-qualified naming 增加了 tool name 的长度，但消除了 namespace 冲突

**架构师视角推断**:
- **粒度考量**: JSONRPC 被拆分为 `dsh-jsonrpc`（protocol）和 `dsh-jsonrpc-agent`（agent integration），说明团队认为 protocol 和 agent integration 的演进速度不同
- **时机判断**: MCP 标准化在 JSONRPC 重构之前完成，是因为 MCP 是 JSONRPC 的上游依赖
- **后续影响**: MCP 标准化降低了与第三方 MCP server 集成的 friction，JSONRPC 的 plugin 架构为后续的扩展提供了基础

**重点关注的文档/代码**:

**领域建模洞察**（DDD 视角）:

### 阶段 4: Session-Query 关系追踪与性能优化

**涉及的 Commits**: `320de5466a`, `7351f07995`, `8e019f2a65`, `be0d44183d`, `75de01f06d`

**阶段意图**: 引入 session 间的关系追踪能力，同时优化 provenance validation 的性能。

**开发者视角推断**:
- **思维模型**: 开发者在构建"session 的关系图"——每个 session 可以追踪其 parent/child 关系，形成一棵 delegation 树
- **优先级选择**: 先实现关系追踪（核心能力），再优化性能（确保可用性），最后内联错误处理（提升调试体验）

**架构师视角推断**:
- **粒度考量**: Session-Query 的关系追踪作为一个独立的能力被引入，而非集成到 session 本身，说明团队认为 query 是一个独立的关注点
- **时机判断**: 在 session-query 的基础能力稳定后才引入关系追踪，是因为关系追踪依赖于 session 的 provenance 数据
- **后续影响**: 关系追踪为后续的 session debug、审计、权限控制提供了基础
