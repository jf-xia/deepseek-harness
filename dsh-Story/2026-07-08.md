## 2. 设计模式与重构

- **应用的设计模式**：
  - **Capability Seam Pattern** — code-execution seam（`ctx.codeRuntime`）完整实现了 Service Definition / Provider / Consumer 三角色：Definition 定义代码执行接口，worker-thread runtime 作为 Provider，run_code tool 作为 Consumer
  - **Strategy Pattern** — tool-timeout policy 从 ToolDefinition 读取 timeoutMs，而非从 config，实现了"tool 自声明超时"的策略
  - **Chain of Responsibility** — repeat-tool-guard 作为 agent loop 的 guard 插件，在 tool 执行前检查重复调用
  - **Observer Pattern** — tool-output spill seam 通过 policy 控制 tool output 的持久化行为

- **模块解耦与接口定义**：
  - `agent/request-messages` 重命名为 `agent/request-advice`（`e97fffeab7`），语义更精确：这是 advice（建议）而非 message（消息）
  - session-prefix 替代 per-step advice seam（`ea4c10d753`），将 agent loop 的 session 上下文管理从 step 粒度提升到 session 粒度
  - skill providers 的拆分（`f453ba77a2`）将 skill 的 provider 注册从单一模块分离为独立的 provider 实现

- **基础设施与性能**：
  - tool-output spill seam（`463b72ce96`）实现了 tool output 的局部持久化，防止大 output 占用过多内存
  - compact token pressure 修复（`e6bd6cc9be`）确保 logged session prefix 被计入 token pressure，避免上下文溢出

## 3. 特性交付与系统影响

- **核心特性**：
  - **Code Mode**（`b59d245c7c`）— registry 的 mode config、SDK codegen、run_code bridge，使 agent 能在 code 执行模式下工作
  - **Worker-Thread Code Runtime**（`583704ac1d`）— `dsh-code-runtime-worker` 提供了基于 `node:worker_threads` 的代码执行运行时
  - **Tool-Timeout Policy**（`8190016e2b`）— tools/execute seam + tool-timeout policy plugin，实现 tool 级别的超时控制
  - **Repeat-Tool-Guard**（`db26ef479d`）— 防止 agent 重复调用同一个 tool 的 guard 插件
  - **ACP Snapshot Extraction**（`556f847064`）— 将 ACP snapshot suite 提取为独立的 support package

- **系统拓扑影响**：
  - Code Mode + Worker-Thread Runtime 构成了 harness 的代码执行能力层，与现有的 bash tool、subagent tool 形成并列的执行通道
  - tool-timeout policy 改变了 tool 执行的控制流，超时检查从 tool 内部提升到 policy 层
  - session-prefix 替代 per-step advice seam，改变了 agent loop 的 session 上下文管理方式

## 4. 架构决策与 Roadmap 对齐

- **关键技术决策（ADR 推断）**：
  - **背景与痛点**：agent 需要在 sandbox 中执行代码，但当前的 bash tool 无法提供隔离的代码执行环境
  - **选择的方案**：引入 Code Mode + Worker-Thread Runtime，通过 `node:worker_threads` 提供隔离的代码执行
  - **Trade-offs**：worker-thread 提供了进程隔离，但增加了 IPC 通信的复杂度；选择 registry-native mode 而非独立的 worker-thread manager，是因为要与 Cordis 的 plugin 体系对齐

  - **背景与痛点**：tool 执行可能超时或被重复调用，缺乏统一的控制机制
  - **选择的方案**：tool-timeout policy 从 ToolDefinition 读取 timeoutMs，repeat-tool-guard 在执行前检查重复调用
  - **Trade-offs**：timeout 从 tool 自声明而非 config 统一管理，增加了灵活性但降低了全局可见性

  - **背景与痛点**：ACP snapshot 测试套件与主代码库耦合，难以独立维护
  - **选择的方案**：提取为独立的 support package
  - **Trade-offs**：增加了 package 数量，但获得了独立的版本管理和测试覆盖

- **产品 Roadmap 支撑**：
  - Code Mode 支撑 "agent 可以在 sandbox 中执行代码" 的产品能力
  - tool-timeout policy 支撑 "tool 执行有超时保护" 的可靠性需求
  - repeat-tool-guard 支撑 "agent 不会陷入重复调用循环" 的稳定性需求

## 5. 开发者/架构师决策推断

- **开发者意图重建**：
  - **思维模型**：开发者在同一天推进了 Code Mode、tool-timeout、repeat-tool-guard、ACP snapshot extraction 四个方向，说明他在构建"agent 的执行与治理"基础设施——agent 需要安全的代码执行环境（Code Mode），需要超时保护（tool-timeout），需要防止重复调用（repeat-tool-guard），需要可维护的测试套件（ACP snapshot extraction）
  - **优先级选择**：先做 Code Mode 的 RFC 重写和实现，再做 tool governance（timeout、guard），最后做测试基础设施（ACP snapshot extraction）
  - **有意取舍**：Code Mode 选择 worker-thread 而非 child_process，是因为 worker-thread 提供了更好的内存共享和更轻量的 IPC；但 worker-thread 的调试和错误处理更复杂

- **架构师决策推断**：
  - **模块拆分粒度**：Code Mode 拆分为三个包（dsh-code-runtime、dsh-code-runtime-worker、dsh-mode），分别承担 seam definition、runtime provider、mode config 的职责
  - **抽象层引入时机**：tool-timeout 在 ToolDefinition 中引入 timeoutMs 字段，而非在 config 中统一管理，是因为 timeout 是 tool 的固有属性，应由 tool 自声明
  - **后续影响**：Code Mode 的 worker-thread runtime 为后续的 sandbox 能力（隔离执行、资源限制）奠定了基础

- **Code Review 视角**：
  - **首先关注**：`b59d245c7c`（Code Mode 的 registry config + SDK codegen + run_code bridge）— 这是一个大型特性，涉及多个模块的协调
  - **会提出的问题**：worker-thread runtime 的错误处理策略是什么？worker 崩溃时如何恢复？tool timeout 与 agent loop 的 quiescence 边界如何交互？
  - **做得好**：repeat-tool-guard 的 ACP snapshot 测试（`a0e39db3b6`, `93d5e4c560`）非常全面，覆盖了多种场景
  - **可以改进**：MCP client 的 e2e 测试（`ace0760927`, `c65e05cff1`）在同一天提交了两次，可能存在测试不稳定的问题
