## 2. 设计模式与重构

- **应用的设计模式**：
  - **Chain of Responsibility** — approval seam 实现了 waterfall of answerers，权限决策通过多个 answerer 的链式处理
  - **Strategy Pattern** — sandbox per-call policy carrier 为每个 bash 调用携带独立的策略，支持不同的沙箱级别
  - **State Pattern** — session-mode core 将 mode 状态作为 session event 记录，mode 变更通过状态机管理
  - **Template Method** — sandbox confinement seam 定义了沙箱的模板，per-platform native runner chains 实现具体的平台适配

- **模块解耦与接口定义**：
  - approval seam 从 bash sandbox 中分离（`ef35007d75`），使权限决策成为一个独立的 capability seam
  - session-mode core 作为独立包 `dsh-mode`（`63ced3e0e2`），mode 状态通过 session event 记录，与 agent loop 解耦
  - session-query checkpoint（`aa1dc0e2c7`）引入了 session 的查询和检查点能力，为后续的 side sessions 奠定基础

- **基础设施与性能**：
  - keyless snapshot refresh mode（`9d2cf8ce82`）使 snapshot 测试不需要 API key，降低了测试门槛
  - workflow workerthread 的 lifecycle fixes（`64b4e2ed2d`, `5f7177a0a9`）提升了 worker-thread 的稳定性

## 3. 特性交付与系统影响

- **核心特性**：
  - **Sandbox Confinement**（`7b8c3a9b40`）— confinement seam + per-platform native runner chains，为 bash 执行提供沙箱隔离
  - **Approval Seam**（`ef35007d75`）— 一次性权限决策，通过 waterfall of answerers 处理权限请求
  - **Session-Mode Core**（`63ced3e0e2`）— logged per-agent policy state，mode 状态作为 session event 记录
  - **Exit Plan Mode**（`edc065666f`）— exit_plan_mode tool + ACP session-mode picker + scriptable review answers
  - **Session-Query Checkpoint**（`aa1dc0e2c7`）— session 的查询和检查点能力

- **系统拓扑影响**：
  - sandbox + approval 改变了 bash 执行的安全模型，从"信任 agent"变为"agent 需要权限决策"
  - session-mode core 改变了 agent 的行为决策路径，mode 状态成为 session log 的一等公民
  - session-query 为后续的交互式 side sessions 和 handback 机制奠定了基础

## 4. 架构决策与 Roadmap 对齐

- **关键技术决策（ADR 推断）**：
  - **背景与痛点**：bash 执行缺乏沙箱隔离，agent 可以执行任意命令，存在安全风险
  - **选择的方案**：引入 sandbox confinement seam + per-platform native runner chains，为每个 bash 调用提供沙箱隔离
  - **Trade-offs**：增加了执行的复杂度和性能开销，但获得了安全保障；选择 native runner 而非 container，是因为需要跨平台支持

  - **背景与痛点**：权限决策散落在各个 tool 中，缺乏统一的权限管理
  - **选择的方案**：引入 approval seam，通过 waterfall of answerers 处理权限请求
  - **Trade-offs**：增加了权限管理的复杂度，但获得了统一的权限决策机制

  - **背景与痛点**：agent 的 mode 状态不可追溯，mode 切换无法审计
  - **选择的方案**：引入 session-mode core，mode 状态作为 session event 记录
  - **Trade-offs**：增加了 session log 的事件类型，但获得了完整的 mode 变更审计链路

- **产品 Roadmap 支撑**：
  - sandbox + approval 支撑 "agent 在受控环境中执行" 的安全需求
  - session-mode core + exit_plan_mode 支撑 "agent 可以分步审查和执行" 的产品能力
  - session-query 为后续的 "交互式 side sessions" 和 "上下文回溯" 奠定基础

## 5. 开发者/架构师决策推断

- **开发者意图重建**：
  - **思维模型**：开发者在同一天推进了 sandbox、approval、session-mode、session-query 四个方向，说明他在构建"agent 的安全与交互"基础设施——agent 需要在受控环境中执行（sandbox），需要权限决策（approval），需要可审计的策略状态（session-mode），需要查询和检查点能力（session-query）
  - **优先级选择**：先做 sandbox + approval（安全），再做 session-mode + exit_plan_mode（交互），最后做 session-query（查询），遵循"安全→交互→查询"的顺序
  - **有意取舍**：sandbox 选择 native runner 而非 container，是因为需要跨平台支持，但牺牲了更强的隔离性

- **架构师决策推断**：
  - **模块拆分粒度**：sandbox、approval、session-mode 作为三个独立的 capability seam，分别承担沙箱、权限、策略的职责
  - **抽象层引入时机**：在 agent scoping 和 tool-cordis 稳定后引入 sandbox 和 approval，是因为这些能力需要与 scoped registries 和 tool registry 协调
  - **后续影响**：sandbox + approval 为后续的 subprocess sandbox、escalation、scripted permission answers 等特性奠定了基础

- **Code Review 视角**：
  - **首先关注**：`7b8c3a9b40`（sandbox confinement seam + native runner chains）— 这是一个安全关键特性，涉及跨平台的沙箱实现
  - **会提出的问题**：sandbox 的性能影响是什么？native runner 的错误处理策略是什么？approval 的 answerer 链如何处理超时？
  - **做得好**：approval seam 的 waterfall 设计非常优雅，通过链式处理支持灵活的权限决策
  - **可以改进**：session-mode 的 RFC（`2929164da9`）删除了中文 counterpart，建议保留 bilingual pair 以支持 i18n
