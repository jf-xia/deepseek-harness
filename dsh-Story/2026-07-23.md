## 2. 设计模式与重构

### 应用的设计模式

- **Unified Send Pattern**：`feat(agent): unify send(target × wakeup), coalesce context/message into user/message` 将发送接口统一为 `target × wakeup` 的组合，消除了 `context` 和 `message` 的二义性。这是典型的 **Command Pattern** 重构。
- **Eager Persistence**：`refactor: eagerly persist session events` 将会话事件的持久化从懒加载改为急切模式，体现了 **Write-Through Cache** 模式。
- **Chain Slot Kind**：`feat(gui): chain slot kind with select routing and renderSlotChain` 引入了链式 slot 模式，支持复杂 UI 组件的组合。

### 模块解耦与接口定义

- **Agent Loop 简化**：`refactor(agent-loop): simplify observable state machine` 和 `refactor(agent-loop): simplify turn driver` 通过简化状态机和 turn driver，减少了内部状态的复杂度。
- **Session Query 统一**：`refactor(session-query): unify query service` 将分散的查询逻辑统一到单一服务中。
- **Send Options 重构**：`refactor(agent): require explicit send options` 和 `refactor(agent): require complete send options` 强制要求显式传递发送选项，消除了隐式默认值。

### 基础设施与性能

- **Eager Session Persistence**：PR #570 `refactor/eager-session-persistence` 将会话事件的持久化从延迟模式改为立即模式，提高了数据安全性。
- **CI 企业级优化**：`ci: isolate enterprise Linux critical paths` 和 `ci: rebalance paid runner gates` 优化了企业级 CI 的资源分配。

## 3. 特性交付与系统影响

- **多模态图片输入**：`Add web multimodal image attachments` 支持在 Web 端上传多模态图片。

- **Chain Slot Kind** 改变了 GUI 组件的组合方式，影响了 web、gui 等 UI 组件。

## 4. 架构决策与 Roadmap 对齐

### 关键技术决策（ADR 推断）

- **背景与痛点**：Agent Loop 的消息状态机过于复杂，send 接口存在 `context` 和 `message` 的二义性，会话持久化的延迟模式可能导致数据丢失。
- **选择的方案与 Trade-offs**：
  - Send Unify：选择将 `context/message` 合并为 `user/message`，简化了接口但可能需要更新所有消费者。
  - Eager Persistence：选择立即持久化而非延迟批量，提高了数据安全性但可能增加 I/O 开销。
  - Chain Slot Kind：选择引入链式 slot 而非嵌套组件，简化了组合逻辑但可能限制了灵活性。

### 产品 Roadmap 支撑

- Web Markdown 渲染支撑了助手消息的可读性。
- 多模态图片输入支撑了多模态交互能力。
- Chain Slot Kind 支撑了复杂 UI 组件的组合。

## 5. 开发者/架构师决策推断

### 开发者意图重建

- **思维模型**：开发者在 7 月 23 日面临多个并行工作流的合并压力（send-unify、eager-persistence、web-gui、session-query），需要在保持主干稳定的同时推进多个特性。
- **优先级选择**：优先处理 Agent Loop 的简化（影响核心稳定性），然后是 Send Unify（影响接口一致性），最后是 UI 增强（影响用户体验）。
- **有意取舍**：选择将 `context/message` 合并为 `user/message`，虽然需要更新所有消费者，但消除了长期的二义性问题。

### 架构师决策推断

- **模块拆分粒度**：Agent Loop 的简化反映了对"单一职责"的坚持，将复杂的状态机拆分为更小的、可管理的组件。
- **抽象层引入时机**：Chain Slot Kind 的引入时机恰到好处——在 GUI 组件组合需求明确后，而非过早抽象。
- **对后续可扩展性的影响**：Send Unify 为后续的消息路由和处理奠定了基础。

### Code Review 视角

- **首先关注**：Eager Persistence 的实现——这类变更如果处理不当可能导致数据一致性问题。
- **会提出的问题**：
  1. Eager Persistence 是否会影响性能？如何测量？
  2. Send Unify 的向后兼容性如何保证？
  3. Chain Slot Kind 是否支持所有现有的 GUI 组件？
- **做得好**：Agent Loop 的简化非常有价值，减少了内部状态的复杂度。
- **可以改进**：Session Query 的统一应该考虑与现有查询接口的兼容性。

## 6. 技术债务与风险评估

### 已知风险 / 变通方案

- **Send Unify 的消费者更新**：所有使用旧接口的消费者都需要更新，这是一个大规模的变更。
- **Eager Persistence 的性能影响**：需要监控 I/O 开销，确保不会成为瓶颈。
- **Chain Slot Kind 的组合限制**：需要验证所有现有的 GUI 组件都能与新的 slot 类型兼容。

### 建议的下一步

1. 为 Send Unify 添加迁移指南和兼容性层。
2. 为 Eager Persistence 添加性能基准测试。
3. 为 Chain Slot Kind 添加集成测试，覆盖所有 GUI 组件。
