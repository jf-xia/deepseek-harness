## 2. 设计模式与重构

### 应用的设计模式
- **迭代硬化模式（Iterative Hardening）**: Session Query 经历了 4 轮连续修复（round 4 → 7），每轮修复前一轮 reviewer 发现的边界情况。这是一种典型的"安全优先"演进路径，先确保核心功能正确，再逐步加固边界。
- **简化重构模式（Simplification Refactoring）**: One-Send-One-Turn RFC 提出将 agent-loop 的 turn 语义简化为"每次 send 独立一个 turn"，消除了之前 turn 内部复杂的状态机。
- **专用化模式（Specialization）**: TUI 从通用 UI 组件中独立为专用包，遵循了"单一职责原则"。

### 模块解耦与接口定义
- **TUI 独立化**: `packages/client/` 中的 TUI 功能被提取为独立包，降低了 UI 层与业务逻辑的耦合。
- **Agent Loop turn 语义简化**: 将 turn 的生命周期从多步状态机简化为"每个 send = 一个 turn"，减少了状态转换路径。

### 基础设施与性能
- **SQLite 权限硬化**: 创建数据库时强制 owner-only 权限（`96975f3`），防止多用户环境下的数据泄露。
- **FTS 谓词规划保护**: Session Query 在 FTS 查询前增加了预检查（`e8abfd6`），防止无效查询导致的 SQLite 错误。

## 3. 特性交付与系统影响

### 核心特性
- **One-Send-One-Turn**: 每个 `send()` 调用创建独立的 turn，简化了 agent-loop 的状态管理。这对后续的 cancellation、error recovery 和 telemetry 都有深远影响——每个 turn 的边界更清晰。
- **TUI 专用包**: 为终端 UI 提供了独立的包结构，支持 theme-agnostic 的颜色方案，为后续的 Windows terminal 兼容性奠定了基础。
- **Session Query 多轮修复**: 从 round 4 到 round 7 的连续修复，确保了 SQLite FTS 查询的正确性和健壮性。

### 系统拓扑影响
- Session Query 的修复影响所有依赖 `ctx.sessionQuery` 的消费者（ACP、TUI、SDK）。
- One-Send-One-Turn 改变了 agent-loop 的核心语义，影响所有通过 `ctx.agentLoop` 驱动的上层逻辑。

## 4. 架构决策与 Roadmap 对齐

### 关键技术决策（ADR 推断）

**决策 1: One-Send-One-Turn 简化**
- **背景与痛点**: 原有 turn 语义允许多个 send 在一个 turn 内执行，导致 turn 边界模糊，cancellation 和 error recovery 的实现复杂度高。
- **选择的方案与 Trade-offs**: 选择"每次 send = 一个 turn"，牺牲了多 send 合并的灵活性，换取了更清晰的生命周期边界和更简单的状态管理。
- **推断依据**: `a425aff` docs(rfc): propose one-send-one-turn simplification, `aa4e629` feat(agent-loop): give each send its own turn

**决策 2: Session Query 迭代硬化而非一次性重写**
- **背景与痛点**: Session Query 的 FTS 查询存在多个边界情况（类型错误、绑定预检、谓词规划）。
- **选择的方案与 Trade-offs**: 选择逐轮修复而非重写，保持了现有接口的稳定性，但增加了多轮 review 的开销。
- **推断依据**: `75e9958` → `e8abfd6` 的 4 轮连续修复

### 产品 Roadmap 支撑
- One-Send-One-Turn 为后续的 goal-based loop、plan mode 和 LLM error recovery 提供了更清晰的 turn 边界。
- TUI 专用包为后续的 desktop harness workbench 和 Windows terminal 支持铺平了道路。

## 5. 开发者/架构师决策推断

### 开发者意图重建
- **思维模型**: 开发者在处理 session query 的边界情况时，采用了"修一个发现下一个"的增量修复策略，而非全面审计。这表明 session query 模块的复杂度超出了初始设计预期。
- **优先级排序**: 先修复 session query/persistence 的正确性问题（安全优先），再推进 one-send-one-turn 的架构简化（演进优先），最后处理 UI 和文档（体验优先）。
- **有意取舍**: One-Send-One-Turn 的 RFC 明确标注为"proposal"，表明这是一个有意的渐进式变更，而非急于求成的重构。

### 架构师决策推断
- **模块拆分粒度**: TUI 的独立化遵循了"UI 与业务逻辑分离"的原则，但独立为包的粒度选择（而非仅作为子模块）表明团队预期 TUI 将有独立的发布节奏。
- **抽象层引入时机**: One-Send-One-Turn 在 session query 稳定后引入，表明团队有意在基础稳定后再推进架构演进。
- **后续影响**: turn 语义的简化为后续的 goal-based loop、plan mode 和 LLM error recovery 提供了更清晰的状态机基础。
- **作为架构师**: 我赞同 session query 的迭代硬化策略——在正确性和性能之间选择了正确性。但 one-send-one-turn 的 RFC 需要更多关于 backward compatibility 的分析。

### Code Review 视角
- **首先关注**: `62f6251` fix(agent-loop): reclassify pending tool calls——这是 agent-loop 的核心语义变更，需要仔细审查。
- **会提出的问题**: one-send-one-turn 对现有 session log 格式的影响是什么？是否需要 migration？
- **做得好**: Session query 的多轮修复策略很好，每轮都有明确的 review feedback 驱动。
- **可以改进**: Windows 路径修复（`e00d04a`, `a921fcb`）应该有对应的测试覆盖。

## 6. 技术债务与风险评估

### 已知风险 / 变通方案
- **Session Query FTS 谓词规划**: round 7 修复了 guard，但 FTS 的性能特性在大数据量下可能需要进一步优化。
- **One-Send-One-Turn 的 backward compatibility**: RFC 提案阶段，需要评估对现有 session log 格式和 replay 机制的影响。
- **Windows 路径兼容**: 修复了 generated paths 和 package manifests，但 fs-local 的 POSIX-only mode-bit 断言可能在 Windows 上有问题。

### 建议的下一步
- 为 one-send-one-turn 添加 session format version 变更记录。
- 为 Windows 路径修复添加跨平台测试。
- 对 session query 进行性能基准测试，验证 FTS 在大数据量下的表现。
